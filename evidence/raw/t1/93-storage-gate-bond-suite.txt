## T011 — what a consumer can still see after a slash

[PASS] test_slashIsInvisibleToHealthAndToTheGuard() (gas: 369680)
Suite result: ok. 2 passed; 0 failed; 0 skipped; finished in 2.22ms (547.70µs CPU time)

measured on the real Makhzan, deal 1, 1e15 planck bond:
  healthOf inside the challenge window                 2   (guard refuses, Pending)
  healthOf past the deadline, before resolve           3   (guard refuses, Default)
  providerOf(provider).bond, 20% slash applied         8e14 (1e15 -> 8e14)
  healthOf immediately after resolve                   1   (guard says healthy)
  healthOf ten blocks later                            1   (still healthy)
  providerOf(provider).bond ten blocks later           8e14 (the slash stays)

conclusion: `healthOf` and `MakhzanGuard.isHealthy` cannot see a past default. The only public view
that remembers it is the provider bond: `providerOf(address who) -> (uint16 id, uint64 bond,
uint24 activeDeals, bool registered)`. Makhzan exposes no providerId -> address view, so a consumer
holding only a dealId cannot look the bond up directly; it has to go through an address.

plus the unchanged suites (lock 9, release 10, refund 10, fuzz 3):
Ran 5 test suites in 225.01ms: 41 tests passed, 0 failed, 0 skipped (41 total tests)

what the nine tests pin:
  - lock stores the floor; 0 is the default and keeps the old behaviour (release still pays after
    a slash when minBond == 0)
  - bond == floor passes (>=, not >)
  - slash 1e15 -> 8e14 drops the bond under a 9e14 floor: release reverts BondTooLow, value stays
    in the gate, status stays 1 (locked)
  - the floor is read at release time, not lock time: a 2e14 top-up (back to 1e15) re-opens release
  - a payee that is not the deal's provider reads as a zero bond, so any floor > 0 refuses
  - refund is untouched by the floor: default pays the payer; after resolve the deal is healthy
    again, so an in-term refund is still refused
  - health still wins: a pending challenge refuses with Pending even with a high bond

deviation, recorded: Makhzan has no providerId -> address view, so the gate resolves the provider
through the payee and requires `providerOf(payee).id == dealOf(dealId).providerId`. Payee is
therefore expected to be the deal's provider. Any other payee has no bond to prove and cannot
satisfy a floor > 0. This is documented in the storage-layout comment and the README, and it is
the one simplification in this round. The `registered` flag is not checked separately: an
unregistered payee has id 0 and a real deal's providerId is never 0.
