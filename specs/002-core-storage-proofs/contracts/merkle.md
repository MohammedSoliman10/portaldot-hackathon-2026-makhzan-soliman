# Merkle Specification (normative)

**Feature**: `002-core-storage-proofs` | **Constitution**: Principles XV and XVI

Both the on-chain verifier and the off-chain tree builder MUST implement exactly this. The shared
golden vectors are the check.

## Hashing

```text
leafHash(bytes)      = keccak256(0x00 ‖ bytes)
nodeHash(left,right) = keccak256(0x01 ‖ left ‖ right)
```

The prefixes are single bytes and are never optional. A leaf is always hashed from the supplied
bytes; a precomputed leaf hash is never accepted from the prover.

## Tree construction

1. Leaves are the file's blocks in order: `ceil(size / blockSize)` blocks. Every block except the
   last is exactly `blockSize` bytes; the last is `size − (leafCount − 1) × blockSize` bytes and is
   at least one byte.
2. Each block is hashed with the leaf rule.
3. **Pairing with promotion**: at each level, nodes are paired left to right; when a level has an odd
   number of nodes, the last node is **carried upward unchanged** (promoted) and has **no sibling**.
4. The process repeats until one node remains: the root. For a single leaf the root is that leaf's
   hash (no node hash is applied).

## Path

For a challenged index `i`:

1. Start with the running hash = `leafHash(block_i)`, `idx = i`, `count = leafCount`.
2. While `count > 1`:
   - If `count` is odd **and** `idx == count − 1`: the node is promoted — append no element, keep the
     running hash, then `idx = idx / 2` and `count = (count + 1) / 2`.
   - Otherwise: the sibling is at `idx ^ 1`. Append it to the path. If `idx` is even the running hash
     is the left child (`nodeHash(running, sibling)`); if `idx` is odd it is the right child
     (`nodeHash(sibling, running)`). Then `idx = idx / 2` and `count = (count + 1) / 2`.
3. The path is the appended elements, in the order they were appended (bottom-up).

## Verification (on-chain, normative)

```text
verify(root, bytes data, uint32 index, uint32 leafCount, bytes32[] path) -> bool
  if leafCount == 0 or index >= leafCount   -> reject
  h = leafHash(data); idx = index; count = leafCount; p = 0
  while count > 1:
    if count odd and idx == count-1:  (promoted; no element consumed)
    else:
      if p >= path.length -> reject                       (path too short)
      sibling = path[p]; p += 1
      h = idx odd ? nodeHash(sibling, h) : nodeHash(h, sibling)
    idx = idx / 2; count = (count + 1) / 2
  accept iff p == path.length  and  h == root             (path too long is rejected too)
```

Before calling `verify`, the contract also enforces the **expected byte length** of `data`:

```text
index == leafCount - 1  ->  data.length == size - (leafCount - 1) * blockSize
otherwise               ->  data.length == blockSize
and data.length > 0 in every case
```

`index`, `leafCount` and `size` come from the deal, never from the caller. Path directions come from
`index` and `count`, never from the prover.

## Worked vectors

`packages/merkle-vectors/vectors.json` (generated by `packages/merkle-vectors/generate.ts`) holds, for
leaf counts 1, 3, 7 and 1000: the leaf bytes, the leaf hashes, the root and every element of every
path. The generator writes the same bytes to `contracts/test/fixtures/vectors.json`, which is the copy
`GoldenVectors.t.sol` reads; `generate.ts --check` compares both copies against a fresh generation, so
they cannot drift. The TypeScript test reads `packages/merkle-vectors/vectors.json`.

| Leaf count | Tree shape | Path lengths present | Promotion happens |
| --- | --- | --- | --- |
| 1 | single leaf | 0 | root is the leaf hash |
| 3 | L0 L1 L2 → [h0 h1] promote h2 → [h01 h2] | 2 (indices 0,1), 1 (index 2) | level 1 promotes `h2` |
| 7 | 7 → 4 → 2 → 1 | 3 (most), 2 (index 6) | levels 7→4 and 4→2 promote |
| 1000 | 1000 → 500 → … | varying | several levels; includes both parities |

## Position binding

The verifier binds a proof to `(root, index, leafCount, data, path)`; path directions come from
`index` and `count`, never from the prover. Two properties are tested:

1. A proof produced for index `i` is accepted at `i` and rejected at every `j ≠ i` (the same path
   replayed at another index), with one documented exception: when the bytes at `i` and `j` and every
   sibling hash that differs between the two paths make the two root computations identical — which
   happens only when the blocks, or whole subtrees, involved are byte-identical — the proof is
   accepted at both. This is deliberate. The answer still proves possession of exactly those bytes,
   and one stored copy honestly answers either challenge; it does not reduce what a provider must
   store. `MerklePositionBinding.t.sol` documents the exception and proves distinct blocks never
   share a proof; the fuzz property uses pairwise-distinct leaf contents so it tests the binding
   rather than the exception.
2. A path with the elements reordered, or with one element added or removed, is rejected.

## Change control

Changing prefixes, pairing, promotion or the direction rule is a breaking change: it regenerates the
vectors, updates this document, `MerkleLib.sol` and `apps/makhzan/src/merkle.ts` in one commit, and
CI's parity check proves the two sides still agree.
